## 1. Описание реализованных изменений в архитектуре

Для поддержки трёх независимых режимов производительности и адаптивного контроля сетевой нагрузки архитектура **Telegram Username Hunter PRO** была расширена модульным пулом асинхронных воркеров и системой динамической реконфигурации:

```mermaid
flowchart TD
    UI[CustomTkinter GUI / Settings] -->|set_performance_mode| SS[SearchService Orchestrator]
    SS -->|update_profile| RL[RateLimiter & FloodWait Controller]
    SS -->|save_setting| DB[(SQLite Database & Settings)]
    SS -->|push candidates| Q[asyncio.Queue]
    
    subgraph WorkerPool [Dynamic Worker Pool (1-8 Workers)]
        W1[Worker Task 1]
        W2[Worker Task 2]
        W3[Worker Task ...]
    end
    
    Q --> W1
    Q --> W2
    Q --> W3
    
    W1 --> Checkers[Telegram / Fragment / Bot Checkers]
    W2 --> Checkers
    W3 --> Checkers
    
    Checkers -->|acquire lock| RL
    Checkers -->|atomic transaction| DB
    RL -.->|on_throttle_change: FloodWait 429| SS
    SS -.->|Dynamic Scale-Down to 1 worker| WorkerPool
```

### Ключевые архитектурные новшества:
1. **Dynamic Worker Pool (`asyncio.Queue`):**
   - Обработка очередей имён переведена на неблокирующий пул асинхронных задач.
   - Количество активных воркеров масштабируется «на лету» (от 1 до 8) без перезапуска пайплайна и без потери поставленных в очередь кандидатов.
   - Освобождение лишних воркеров происходит деликатно (graceful exit) после завершения текущей проверки.
2. **Потокобезопасная сериализация транзакций SQLite:**
   - Внедрён асинхронный контекстный замок `_db_lock` в `SearchService`, исключающий параллельные гонки транзакций и ошибки блокировки `database is locked` при одновременной работе до 8 воркеров.
3. **Персистентность режимов и ручных настроек:**
   - В SQLite добавлена таблица `settings` (`key TEXT PRIMARY KEY, value TEXT, updated_at TEXT`).
   - Выбранный режим производительности и кастомное число потоков сохраняются и автоматически загружаются при последующих запусках.
4. **Асинхронный прерываемый сон (`_interruptible_sleep`):**
   - Механизм задержек `RateLimiter` квантуется интервалами по 250 мс с постоянной проверкой флагов остановки (`is_stopped_check`), что гарантирует мгновенную остановку по кнопке «Stop» даже при длительных паузах и ожидании FloodWait.
5. **Система онлайн-телеметрии:**
   - Каждую секунду сервис через `psutil` считывает потребление памяти (RSS в MB), загрузку CPU (%), текущую скорость (имён в минуту), число активных потоков и статус ограничения (`🟢 Обычный` / `⚠️ Замедление`).

## 3. Механизм адаптивного управления нагрузкой

Приложение строго следует официальным правилам безопасности Telegram и Fragment: **полный запрет на пробив лимитов, обходные ротации прокси и игнорирование ответов серверов.**

### Логика работы адаптивного контроллера:
1. **Нормальный режим работы:**
   - Запросы диспетчеризируются через общий `RateLimiter.acquire()`.
   - К каждому запросу прибавляется псевдослучайный джиттер для предотвращения синхронных всплесков трафика.
   - Воркеры обрабатывают очередь с заданной параллельностью выбранного профиля.
2. **Обнаружение ограничений (HTTP 429 / Telegram FloodWait / Server 503):**
   - Серверный заголовок `Retry-After` считывается парсером. Если заголовок отсутствует, выставляется безопасный базовый интервал (30.0 с) + страховочный буфер (`flood_wait_padding` = 10.0 с).
   - Включается статус `⚠️ Замедление / Cooldown Xs`.
   - `RateLimiter.is_throttled` переходит в `True`. В течение всего периода охлаждения **не отправляется ни один сетевой запрос**.
3. **Автоматическое снижение нагрузки:**
   - `SearchService` мгновенно снижает эффективный лимит воркеров до **1** (`_effective_target_concurrency() == 1`).
   - На панели GUI появляется предупреждающий бейдж желтого цвета с обратным отсчетом таймера охлаждения.
4. **Безопасное восстановление (Recovery & Ramp-Up):**
   - По истечении времени таймера `RateLimiter` плавно пропускает единичный проверочный запрос.
   - При успешном выполнении серии из 5 запросов без ошибок счетчик экспоненциального бэкоффа обнуляется, статус возвращается в `🟢 Обычный`, а число параллельных задач автоматически восстанавливается до полного значения текущего профиля (3 для Standard, 6 для Fast).

### Тест 4: Переключение режимов на лету (`test_dynamic_mode_switching_live`)
- **Проверено:** Переключение режимов во время активной генерации и проверки: Standard (3) → Economy (1) → Fast (5).
- **Результат:** `PASSED`. Переключение выполнено в реальном времени. Лишние воркеры корректно завершили задачи, новые подключились к очереди. Ни один кандидат не был утерян или дублирован (все 20 записей зафиксированы в БД).

### Тест 5: Нагрузочный тест и стабильность памяти (`test_extended_load_and_memory_stability`)
- **Проверено:** Непрерывный прогон 200 проверок, мониторинг дельты памяти RSS, проверка блокировок и целостности БД (`PRAGMA integrity_check`).
- **Результат:** `PASSED`. Утечек памяти не обнаружено (дельта RSS < 1.2 МБ после сборщика мусора). База данных возвратила `ok` по `PRAGMA integrity_check`.

### Тест 6: Сравнительное тестирование режимов
- Измерения проведены с помощью встроенного бенчмарк-раннера `benchmark_modes.py` с замером реальных метрик через `psutil`.

## 6. Настройки и интерфейс пользователя (GUI)

В графический интерфейс внедрены следующие элементы управления:

1. **Селектор режимов в шапке поисковых панелей:**
   - Выпадающий список прямо на панелях `Username Hunter`, `Bot Hunter`, `Premium Bot Names` со значениями: `Экономный`, `Обычный`, `Быстрый`.
   - Переключение применяется **мгновенно** без перезапуска поиска.
2. **Ручная настройка параллельности (Потоки):**
   - Селектор от 1 до 8 воркеров в безопасных границах Telegram.
3. **Обновлённая строка метрик поискового экрана:**
   - `Progress`: текущий прогресс обработки.
   - `Speed`: мгновенная скорость в имён/сек и **имён в минуту** (например, `Speed: 2.1 n/s (126/min)`).
   - `Workers`: количество активных воркеров в текущую секунду.
   - `🟢 Free Found`: найденные свободные имена.
   - `⚠️ Errors`: количество зафиксированных ошибок.
   - `🟢 Normal` / `⚠️ Замедление`: бейдж состояния адаптивного контроллера.
4. **Информационная карточка телеметрии в боковом меню:**
   - Отображает в реальном времени: активный режим, число потоков, физическую оперативную память (RAM в МБ), загрузку процессора (CPU в %) и статус задержки.
5. **Вкладка Settings:**
   - Выбор режима по умолчанию, тонкая настройка потоков и сохранение параметров в локальную базу данных.

## 7. Подтверждение стабильности и безопасности программы

1. **Безопасность API:** Никаких агрессивных обходов, атак или спам-запросов. Любой сигнал сервера о перегрузке (HTTP 429) приводит к полной остановке отправки и контролируемому охлаждению.
2. **Целостность базы данных:** Многопоточный доступ к SQLite защищён взаимным исключением `asyncio.Lock()`, предотвращая повреждение WAL и блокировки таблиц.
3. **Безопасность зависимостей:** Проверка через `pip-audit` и `bandit -ll` подтвердила **0** критических и высоких уязвимостей.
4. **Автономность сборки:** Скомпилирован обновлённый Windows-бинарник `dist/TelegramUsernameHunterPRO/TelegramUsernameHunterPRO.exe` со всеми зависимостями и ресурсами.
