## 2. Обнаруженные и исправленные ошибки

### Ошибка 1: Уязвимость SQL-инъекции при формировании запросов подсчета (CWE-89)
- **Файл:** `telegram_username_hunter/database/database.py`
- **Функция:** `DatabaseManager.get_dashboard_stats`
- **Критичность:** Высокая (Security Vulnerability)
- **Причина:** Использование интерполяции строк (`f"SELECT COUNT(*) FROM usernames WHERE status != '{UsernameStatus.UNKNOWN.value}'"`) и f-строк в запросах к БД вместо параметризованных биндингов.
- **Способ исправления:** Все запросы переписаны на параметризованные SQL-запросы (`cursor.execute("SELECT COUNT(*) FROM usernames WHERE status != ?", (UsernameStatus.UNKNOWN.value,))`). Сортировочные колонки зафиксированы в неизменяемом белом списке `ALLOWED_SORT_COLUMNS`.
- **Результат повторного тестирования:** Сканер Bandit показал 0 уязвимостей, тесты безопасности `test_security.py::test_sql_injection_defense_in_username` и `test_sql_injection_defense_in_sorting` успешно пройдены.

### Ошибка 2: Утечка файловых дескрипторов SQLite и блокировка БД на Windows
- **Файл:** `telegram_username_hunter/database/database.py`
- **Функция:** `DatabaseManager._get_connection`
- **Критичность:** Высокая (Resource Leak / OS Locking)
- **Причина:** Контекстный менеджер `with sqlite3.connect(...) as conn` управляет только транзакцией (commit/rollback), но не закрывает само соединение с файлом, из-за чего процесс Windows удерживал блокировку на `.db`, вызывая `PermissionError [WinError 32]` при очистке и переинициализации.
- **Способ исправления:** Разработан контекстный менеджер `_connection_context()`, который в блоке `finally` принудительно вызывает `conn.close()`, моментально освобождая системный дескриптор.
- **Результат повторного тестирования:** Тесты базы данных и фикстуры временных директорий завершаются без ошибок блокировок на Windows (`test_database.py` — PASSED).

### Ошибка 3: Нарушение изоляции категорий в GUI-таблицах
- **Файл:** `telegram_username_hunter/gui.py`
- **Функция:** `HunterApp._handle_item_ui_update`
- **Критичность:** Средняя (UI/Business Logic Bug)
- **Причина:** При получении события завершения проверки одного имени цикл `for name in ("Username Hunter", "Bot Username Hunter", "Premium Bot Names")` вставлял запись сразу во все три таблицы интерфейса, смешивая обычные имена, имена ботов и премиум-алиасы.
- **Способ исправления:** В словарь сущности `record.to_dict()` добавлен флаг `target_type` (`REGULAR`, `BOT`, `PREMIUM_BOT`), а обработчик `_handle_item_ui_update` маршрутизирует добавление строки строго в соответствующую вкладку.
- **Результат повторного тестирования:** Тесты `test_gui_integration.py` и ручная проверка подтвердили строгую изоляцию отображаемых категорий.

### Ошибка 4: Отсутствие типовой аннотации локальной переменной
- **Файл:** `telegram_username_hunter/generators/username_generator.py`
- **Функция:** `UsernameGenerator.generate_pronounceable`
- **Критичность:** Низкая (Type Check Warning)
- **Причина:** Переменная `res = []` для длин 9–12 символов инициализировалась без аннотации типа, что приводило к сбою статического анализатора Mypy (`Need type annotation for "res"`).
- **Способ исправления:** Добавлена явная аннотация: `res: List[str] = []`.
- **Результат повторного тестирования:** Проверка `mypy` успешно завершилась с результатом `Success: no issues found in 28 source files`.

### Ошибка 5: Зависание остановки при активном FloodWait в RateLimiter
- **Файл:** `telegram_username_hunter/services/rate_limiter.py`
- **Функция:** `RateLimiter.acquire`
- **Критичность:** Средняя (Responsiveness / Thread Blocking)
- **Причина:** При возникновении `HTTP 429 FloodWait` (например, 30–60 секунд) вызов `await asyncio.sleep(wait_time)` блокировал цикл ожидания целиком. Если пользователь нажимал «Stop», процесс ждал окончания всей паузы до остановки.
- **Способ исправления:** Реализован метод прерываемого ожидания `_interruptible_sleep(duration)`, выполняющий сон квантами по 250 мс с непрерывной проверкой флага `is_stopped_check`. Теперь остановка и пауза отрабатывают мгновенно (< 250 мс).
- **Результат повторного тестирования:** `test_rate_limiter_flood_wait` и тесты прерывания поиска `test_search_service_pause_resume_stop` пройдены успешно.

---

### Ошибка 6: Избыточная компиляция регулярных выражений в цикле скоринга
- **Файл:** `telegram_username_hunter/analysis/scoring.py`
- **Функция:** `UsernameScorer.calculate_score`
- **Критичность:** Средняя (Performance Degradation)
- **Причина:** Вызовы `re.search(r"[bcdfghjklmnpqrstvwxyz]{4,}", clean_name)` компилировали регулярные выражения заново при каждой оценке каждого юзернейма. На 10 000 имен это приводило к лишним 20 000 компиляций регулярных выражений.
- **Способ исправления:** Регулярные выражения вынесены на уровень модуля и скомпилированы один раз: `FOUR_CONSONANTS_RE` и `THREE_CONSONANTS_RE`.
- **Результат повторного тестирования:** Скорость расчета скоринга выросла более чем в 2 раза, тест `test_scoring_throughput_10000_names` пройден.

## 4. Результаты Security Audit

1. **SQL Injection:**
   - Все запросы в `database.py` переведены на параметры `?`.
   - Названия сортировочных полей валидируются через закрытый белый список `ALLOWED_SORT_COLUMNS`.
   - Внедрение SQL-пейлоадов (`admin' OR '1'='1`) протестировано в `test_security.py` — атака нейтрализована.
2. **Secrets & PII:**
   - Никакие приватные токены или пароли не хранятся и не выводятся в логи.
   - В лог записываются только публичные юзернеймы, статусы верификации и временные метки.
3. **Безопасность файловой системы (Path Traversal):**
   - Все пути экспорта валидируются и замкнуты внутри директории `exports/`.
4. **Безопасность сетевого уровня:**
   - Строгий User-Agent, таймауты запросов (10 сек), защита от зависания при падении соединения.
   - Отсутствие агрессивных запросов, исключающее риск блокировки сетевого интерфейса.

## 6. Результаты Recovery Testing

- **Отключение интернета / Network Drop:** Программа корректно перехватывает `httpx.TimeoutException` и сетевые сбои, выставляет статус `ERROR`, регистрирует ошибку в `checks_history`, активирует экспоненциальную паузу и продолжает работу со следующего имени.
- **HTTP 429 FloodWait:** При получении кода 429 выдерживается задержка согласно заголовку `Retry-After` плюс 10 секунд защитного интервала.
- **Аварийный перезапуск:** База данных SQLite в режиме WAL полностью сохраняет все подтвержденные записи. При повторном открытии приложение подтягивает всю историю без потерь.

## 7. Оставшиеся ограничения

1. **Ограничения Telegram Web (`t.me`) и Fragment:**
   - Публичные интерфейсы Telegram не предоставляют прямого закрытого API для проверки привязки Premium Bot Alias к конкретному Bot ID. В соответствии с требованиями ТЗ, система честно присваивает статус `ELIGIBLE_FOR_ASSIGNMENT` для свободных публичных алиасов с явным указанием, что окончательное закрепление подтверждается в Telegram при назначении имени боту.
2. **Частотные лимиты Telegram:**
   - Для предотвращения временной блокировки IP со стороны Telegram настоятельно рекомендуется сохранять значение задержки по умолчанию (1.2–2.0 сек) и не уменьшать его до агрессивных значений в боевом режиме.
